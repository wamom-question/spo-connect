## 6. ネットワーク障害時のオフライン・QRデータ同期 & 手動復旧フロー

### 6.1 クライアント（参加者スマホ）のオフライン対応

1. **キャッシュがある場合:**
   - オフライン時でも画面上にQRコードを表示可能。
   - 人による目視確認用として、画面下部に保存されている `db_id`（データベースID）を表示する（ホスト側で手動変更・確認を行う際の照合用）。
2. **キャッシュがない / 異DBID / 新規登録時のオフライン:**
   - ネットワーク未接続かつ有効なキャッシュがない場合や、ユーザー作成フェーズでオフラインになった場合はシステム登録を諦め、アナログ紙（持ち込みノート）による手動記録に切り替える。

### 6.2 キオスク端末の送信待ちキュー（Outbox）と未送信QR一括回収仕様

- **永続的送信待ちキュー（Outbox）の保持:**
  - キオスク端末は、得点操作が発生した瞬間にブラウザの永続ストレージ（IndexedDB または localStorage）内の Outbox（送信待ちキュー） へ操作オブジェクトを即座に保存する。
  - 各操作は `operation_id`（UUID）、操作種別、対象データ、タイムスタンプ、状態（`PENDING` / `NEEDS_RECONCILIATION`）を保持する。
  - サーバーから正常な反映レスポンス（Ack）を受信するまで、ページ更新や端末再起動が行われてもキューから削除してはならない。
- **オフライン時の連続操作受付:**
  - ネットワーク切断中であっても、キオスク端末はOutboxへキューイングを続け、連続してスキャン・操作を受け付ける。
  - バックグラウンドで定期的に自動再送を試行し、オンライン復帰時にはOutbox内の未送信操作を順次サーバーへ自動送信する。
- **未送信QRによる手動一括回収（オフライン・フォールバック）:**
  - **単一モード vs 複数一括モード:** Outbox内に未送信データが1件の場合は「単一QR」、複数件存在する（例: 10件）場合は「一括回収用QR」を生成する。
  - **分割QR・連番・チェックサム:** QRコードの物理的な容量制限（文字数上限）を考慮し、複数操作データは圧縮の上、分割QR形式（例: 1/3, 2/3, 3/3）で順次またはスライド表示する。ペイロードには `batch_id`、総件数、連番、チェックサム（CRC32等）を付与する。
- **ホストアプリ側での取り込み・相互確認プロトコル:**
  - ホストアプリが未送信QR群を読み取った際、チェックサム検証と重複排除を行い、取り込み成功件数・識別子一覧を画面に表示する。
  - ホストアプリは取り込み完了を示す「消去用QR（または同期完了シグナル）」を提示し、キオスク端末がそれを読み取る（またはサーバー経由でAckを受ける）ことで、初めてキオスク側のOutboxから該当操作が安全に消去される。

### 6.3 ホストMacBook（専用アプリ）のオフライン運用、アトミック保存 & データ破損防止プロトコル

ホストアプリがローカルストレージに保持するユーザーごとのJSONファイル（`(データベースID)/(ユーザーID).json` 等）の保存・更新において、プロセス強制終了や電源断によるファイル破損を物理的に防止するアトミック書き込み機構、チェックサム検証、および世代管理を導入する。

- **アトミック書き込み（原子的置換）の義務付け:** ローカルJSONファイルを更新・保存する際は、直接ファイルを上書きするのではなく、**同一ディレクトリ内に一時ファイル（.tmp）を作成して書き込んだ後、ファイルシステムの原子的な置換処理（fs.rename）**を実行する。これにより、書き込み途中の異常終了によるファイル破損や部分的な書きかけデータの発生を完全に防止する。
- **チェックサムおよびメタデータの保持:** 保存されるJSONファイル内には、データ内容の整合性を担保するための SHA-256 チェックサム、最終同期リビジョン、およびタイムスタンプをメタデータとして必ず含める。アプリ起動時やファイル読み込み時にチェックサムの検証を行い、破損や不整合を即座に検知する仕組みとする。
- **世代管理とバックアップ・自動復旧機構:** ローカル保存時には、直前の正常なファイルをバックアップ（例: `.bak` または世代別ローテーション）として一定世代分保持する。万が一、最新のローカルJSONの読み込み時に破損やチェックサム不一致を検知した場合、システムは警告を発するとともに、直前の正常なバックアップ世代から安全にデータを復旧できる機能を備えることで、データ喪失リスクを排除する。
- **オフラインモード移行時:**
  - アプリ上で「オフラインモード」ボタンを押すと、MacBookのカメラ（QRコードリーダー）が起動する。
  - **キオスク端末の「未送信QR」を読み取った場合:** 手動入力を挟むことなく、即座にローカルJSONへ内容を反映・保存する。
  - **参加者の個別の「QRコード」を読み取った場合:** 該当する `(ユーザーID).json` の編集用GUIエディタが開出し、手動で得点やデータを編集・保存できる。
- **オンライン復帰（復活）時の同期フェーズ定義と競合解決プロトコル:**
  通信が回復しても、蓄積されたローカルデータを一括で自動アップロード・自動送信することは禁止する。オンライン復帰時の処理は以下の明示的な状態遷移（ステートマシン）に従って段階的に実行する。
  - **① 再接続 (`RECONNECTING`):** サーバーとのSocket/HTTP通信を再確立する。この段階ではデータ送信・同期処理は一切行わない。
  - **② 差分取得 (`FETCH_DELTA`):** サーバー上の現行リビジョンおよび最新の監査ログ（`score_logs`）のヘッドを取得し、ローカルで保持している未送信操作群（Outbox）との差分を算出する。
  - **③ 同期候補の検証 (`VALIDATING`):** ローカルの操作イベントに含まれる `operation_id` と期待リビジョンを検証する。
  - **④ 競合判定 (`CONFLICT_CHECK`):** サーバー側ですでに適用済みの操作との重複判定、および同一個人の属性変更・得点直接補正に対する競合を判定する。
  - **⑤ 自動統合 / 承認待ちの切り分け:**
    - **自動統合可能:** 一意な `operation_id` を持つ独立した得点操作（キオスクの順位確定や未送信QRの取り込み結果等）であり、かつサーバー側に競合する変更が存在しない場合は「自動統合候補」として処理する。
    - **承認待ち (`PENDING_APPROVAL`):** 得点ボードの表示状態変更、ユーザー情報（名前・チーム）の変更、およびサーバー側で別の修正が挟まっている同一ユーザーに対する操作は、すべて自動適用を一時停止し「同期承認待ち」状態とする。
  - **⑥ 同期承認 (`USER_APPROVAL`):** 「同期ダイアログ（プレビュー画面）」を表示し、自動統合される操作一覧と、手動確認が必要な競合操作の差分（変更前後の値および対象ユーザー）を提示する。管理者が確認の上、「統合実行」をクリックすることで初めて送信を行う。
  - **⑦ 同期適用 & 完了確認 (`APPLY_AND_CONFIRM`):** サーバーへ承認済みイベントを送信し、ACK受信後にローカルの Outbox を消去して同期完了とする。

## 7. クライアント要件 (参加者スマホ)

- **シェイク検知と単調増加カウンター:**
  - DeviceMotion API を用いたシェイク検知では、瞬間的な加算値を直接送信するのではなく、アプリ起動後（または指定集計セッション開始後）からの累計シェイク回数（単調増加カウンター）、または一意の連番付き増分イベントをクライアント側で保持・送信する。
  - リクエストにはセッションID、端末のローカルタイムスタンプ、および `operation_id` を付与し、ネットワーク切断時の再送（リトライ）による二重計上を構造的に防止する。
  - 人間の身体的限界を超える異常な高頻度（例: 秒間50回超など）のカウント増加を検知した場合、サーバー側は不正な申告として自動的に破棄・ロックする。
- **写ルンです風カメラ:**
  - `<input type="file" capture="environment">` で撮影。
  - Canvas API を使用し、アップロード前に「最大幅 1280px 圧縮」「モノクロ/フィルム風トーン」「JPEG品質 0.7」に加工して軽量送信。
